# 配置、历史与归档迁移

换电脑或切换安装渠道时，需要分别保留配置、历史和实际归档。只导出其中一类，不能保证另一台设备可以还原。

![配置与历史分别导出；原生历史导入采用合并去重。](/img/docs/v1-9-6/migration-detail-zh-light-1310.webp)

*配置与历史分别导出；原生历史导入采用合并去重。 界面版本：1.9.6。*

## 先准备三类资料

| 资料 | 包含什么 | 还需要什么 |
| --- | --- | --- |
| 配置导出 | 项目、来源和设置 | 新设备路径、插件和加密密码 |
| `.frhistory` | 仓库信息与不可变历史数据包 | 实际归档和全部依赖 |
| 归档或可信云副本 | 可恢复的文件内容 | 对应历史、来源绑定与解密材料 |

本机工作区、索引、副本定位和 DPAPI 密码材料有设备边界，不会因导出历史而全部搬迁。

## 导出与导入配置

退出旧客户端的自动任务并保存完整数据副本。在设置的“数据迁移”中导出配置；可使用本地 JSON 或经过验证的云连接。

导入配置会替换当前设置，先保存目标设备的原配置。核对来源、备份位置、插件状态和密码；导入 `config.json` 不会使旧路径自动有效，也不会迁移本地密码存储。

## 导出与导入历史

先在历史中打开要迁移的项目，再导出 `.frhistory`，核对其清单中的 `ConfigId`。未选择项目时会使用首个配置，应在导出前明确选择。

传输包包含 `manifest`、`repository.json` 和 `packs`，`IncludesPayloads=false`。原生历史导入合并不可变事实并去重；重复导入同一数据包不会重复添加。无匹配项目时可以形成孤立仓库，不会自动创建完整来源配置。

界面中仍可能出现旧“合并或替换”说明；新版原生历史按合并去重处理，不沿用替换旧 `history.json` 列表的语义。

## 搬迁归档并验证

独立复制归档和增量依赖，或下载可信云副本。旧绝对路径不会自动变成新设备的本地定位；检查来源绑定和实际可用归档，必要时先恢复到新目录。

完成导入后，用测试副本还原，检查文件和应用加载，再恢复自动化。云历史同步不会搬迁本机工作区，也不会按设备时间覆盖另一端的历史。

## 从 1.8 升级或回退

升级时先处理[旧备份接管报告](/docs/getting-started/v1-9-upgrade#193-旧历史接管报告)。删除边界未知的旧版本只使用覆盖还原或新目录恢复。回退到 1.8 使用升级前的独立副本，避免旧客户端修改 1.9 仓库。
